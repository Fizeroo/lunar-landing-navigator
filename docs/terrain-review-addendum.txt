Terrain ray edge-case review addendum
Date: 2026-11-14. Reviewer: t1q, read-only.
Artifact/code: t1p worktree terrain.ts and staged PGDA90 patch.

Concrete blocker found after the initial report:
At the vetted observer site, call analyzeTerrainHorizon(patch, site, observerHeightM=0, azDeg=0, targetAltDeg=...). Observed:
- target altitude -90, -89, -45 degrees => status insufficient, no blocker.
- target altitude -5, -1, 0, +1 degrees => status blocked by farther mesh triangles.
The observer is at a sampled terrain vertex with zero clearance. A downward ray enters the local surface at distance zero. rayTriangle intentionally discards distance <=0.5m, so it drops the self-surface intersection and can return insufficient for an obviously ground-intersecting direction. For a site known to lie on the DEM surface, classify strictly downward rays as blocked by local ground/self-surface (or implement a robust origin-surface rule); add h=0 down/tangent/up tests. I sent this finding directly to t1p.

Finite-coverage handling:
The current terrain ray API has no clear return path: when no triangle intersection is found it returns insufficient, including directions that cross the finite patch boundary. This is conservative and avoids false “clear” from the sphere tangent range. A local triangle hit returns blocked. Preserve that behavior. The smooth sphere block is separately named in the reason string; UI should label it as smooth reference-sphere geometry, not DEM-confirmed terrain obstruction.

Prior artifact validation remains valid:
Live PGDA90 ranged extraction and exact source-window bytes/hash matched; pixel-center inverse projection and xyz reconstruction independently matched exactly. The patch has 0 NaN cells but no companion LDEC/effective-resolution/error layers, so valid-cell count alone does not prove observational support/quality.
